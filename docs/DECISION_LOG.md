# Decision Log

Architecture decisions for `task-manager-api`, recorded per `.claude/rules/adr-standards.md`.

## ADR-001: Framework and Language (FastAPI + Python)

**Status:** Aceptado
**Fecha:** 2026-09-18

### Contexto y Problema

Needed an async-first Python web framework to build a Task Management API within a 4-6h time
box, with strong typing/validation and low boilerplate for auth, RBAC, and rate limiting.

### Opción Elegida y Justificación

FastAPI on Python >=3.12, managed with `uv`. FastAPI gives native async request handling,
Pydantic v2 integration for request/response validation, and auto-generated OpenAPI docs with
minimal setup — all needed for the auth/RBAC/rate-limiting surface without hand-rolled
boilerplate. `uv` was picked over pip/poetry for fast, lockfile-based dependency resolution
(`uv.lock`), keeping install and CI times low.

### Tradeoffs y Consecuencias

- **Positivas (+):** async end-to-end (routes, DB session, JWT checks); free interactive docs at
  `/docs`; Pydantic v2 reused for both config (`pydantic-settings`) and schemas, one validation
  library for the whole app.
- **Negativas (-):** FastAPI's dependency-injection style (`Depends()`) is framework-specific and
  must be kept out of `app/services/` and `app/repositories/` by convention (enforced via code
  review, not tooling) to preserve the Clean Architecture boundary.

## ADR-002: Database and ORM (PostgreSQL + Async SQLAlchemy 2.0)

**Status:** Aceptado
**Fecha:** 2026-09-18

### Contexto y Problema

Needed a relational store with transactional integrity for tasks/users, an async-compatible ORM
matching FastAPI's async request path, and a migration tool that doesn't drift from the ORM's
schema definitions.

### Opción Elegida y Justificación

PostgreSQL 16 accessed via SQLAlchemy 2.0's async engine (`asyncpg` driver), with Alembic driving
schema migrations autogenerated from the SQLAlchemy models. SQLAlchemy 2.0's typed query builder
(`app/repositories/`) also closes off raw/string-interpolated SQL, removing SQL-injection surface
by construction rather than by convention. Alembic connects with a separate DDL-capable
`migrator` Postgres role, decoupled from the app's own DML-only runtime role (see the Security
Audit section of `README.md` for the least-privilege role split).

### Tradeoffs y Consecuencias

- **Positivas (+):** no raw SQL anywhere in the codebase; schema changes are versioned,
  reviewable migration files; least-privilege DB roles limit blast radius of an app-level
  compromise (`app` role has no `CREATE`/`ALTER`/`DROP`).
- **Negativas (-):** async SQLAlchemy 2.0 has a smaller ecosystem/less mature docs than the sync
  API; the ORM/migration split (`app/models/` vs `alembic/versions/`) requires discipline to keep
  autogenerate diffs reviewed rather than blindly applied.

## ADR-003: Testing Strategy and Coverage (pytest + httpx AsyncClient, SQLite for tests)

**Status:** Aceptado
**Fecha:** 2026-09-18

### Contexto y Problema

Needed fast, isolated tests for an async API within the challenge's time box, without requiring
a running Postgres instance for every test run, while still tracking coverage.

### Opción Elegida y Justificación

pytest + pytest-asyncio for async test functions, `httpx.AsyncClient` for in-process HTTP-level
API tests, and `aiosqlite` (in-memory SQLite) as the test database instead of Postgres.
`pytest-cov` reports coverage on every run (`--cov=app --cov-report=term-missing`) with an
internal target of >75% line coverage on `app/`. Given the actual query surface (no
Postgres-only SQL features used), SQLite-in-memory was judged an acceptable tradeoff for speed
and zero external dependencies within a 4-6h box.

### Tradeoffs y Consecuencias

- **Positivas (+):** tests run with no Postgres container, fully isolated per test, fast enough
  to run on every commit; `httpx.AsyncClient` exercises the full ASGI stack (middleware, auth
  dependencies) rather than calling service functions directly.
- **Negativas (-):** SQLite/Postgres parity is not guaranteed — a future Postgres-only feature
  (e.g. a Postgres-specific type or extension) would need its own Postgres-backed test tier
  (tracked as a Pendiente in `README.md`). The >75% coverage target is not currently enforced by
  a `--cov-fail-under` gate; it's tracked by convention only, not blocked in CI.

## ADR-004: Code Quality Pipeline (ruff + mypy + pre-commit; CI/CD deferred)

**Status:** Aceptado
**Fecha:** 2026-09-18

### Contexto y Problema

Needed consistent lint/format/type-check enforcement without maintaining multiple overlapping
tools, and a way to catch issues before they reach `main` — within the challenge's time box,
without spending it standing up a full CI pipeline.

### Opción Elegida y Justificación

`ruff` was chosen as the single tool for linting, formatting, and import sorting, replacing the
flake8/black/isort combination — one tool covering three concerns instead of three tools that can
disagree with each other. `mypy --strict` runs separately for type checking (ruff does not type
check). Both, plus `pytest -m "not slow"`, are wired as local git hooks via `pre-commit`
(`.pre-commit-config.yaml`), running through `language: system` + `uv run` so hooks execute
inside the project's own `uv`-managed venv instead of pre-commit's isolated environments — one
source of truth for tool versions via `uv.lock`. Lint/format/mypy run on `pre-commit`; the test
suite runs on `pre-push` to keep commits fast.

A GitHub Actions CI pipeline (lint/type-check/test on PR, image build/push and container
vulnerability scanning on merge to `main`) was scoped but deliberately deferred — see
`README.md`'s Pendientes — since local pre-commit/pre-push hooks already give the same
enforcement for a single-contributor challenge submission, and standing up CI wasn't justified
inside the 4-6h box.

### Tradeoffs y Consecuencias

- **Positivas (+):** one lint/format tool (ruff) instead of three; hooks run in the real project
  venv, so no version drift between hook and dev environment; enforcement happens before a commit
  exists, not after a PR is opened.
- **Negativas (-):** no CI pipeline yet, so enforcement depends on every contributor having hooks
  installed locally (`make hooks-install`) — nothing blocks a push from an environment where hooks
  weren't installed; no container vulnerability scanning; no automated build/push of the Docker
  image on merge. All tracked in `README.md`'s Pendientes.

## ADR-005: Containerization Approach (Multi-Stage Docker + Docker Compose)

**Status:** Aceptado
**Fecha:** 2026-09-18

### Contexto y Problema

Needed a reproducible way to run the API, its Postgres dependency, and a one-shot migration step
together, while keeping the runtime image minimal and avoiding running the API as root or with a
superuser DB role.

### Opción Elegida y Justificación

A multi-stage `Dockerfile`: a builder stage runs `uv sync` to build the virtualenv, and the
runtime stage copies only the built virtualenv and app code, with no build tools or `uv` present
and a non-root `appuser`. Docker Compose defines three services: `db` (Postgres 16, provisions
least-privilege roles on first boot via `db/init/001_create_roles.sh`), `migrate` (one-shot
`alembic upgrade head` using the DDL-capable migrator role, then exits), and `api` (the
long-running server, using only the DML-only app role). Compose services run with
`security_opt: [no-new-privileges:true]` and `cap_drop: [ALL]`; `api` additionally runs
`read_only: true` with a `tmpfs` for `/tmp`.

### Tradeoffs y Consecuencias

- **Positivas (+):** small runtime image (no build toolchain shipped); non-root, read-only,
  capability-dropped `api` container reduces the impact of a container-level compromise;
  migrations run once via a dedicated role/service rather than on every API container start.
- **Negativas (-):** no TLS termination in-app (assumes a reverse proxy/ingress in front, per
  `README.md`'s Pendientes); Compose alone doesn't give multi-replica orchestration, health-based
  restarts across a cluster, or rolling deploys — out of scope for the challenge's time box.

## ADR-006: Refresh Tokens + Redis-Backed Revocation List

**Status:** Aceptado
**Fecha:** 2026-09-18

### Contexto y Problema

Access tokens were 15-minute JWTs with no way to invalidate them before expiry: no logout, and no
way to force-expire a session (compromised device, password change). Needed refresh tokens for
longer sessions without lengthening the access token's blast radius, plus a way to revoke a
specific token immediately.

### Opción Elegida y Justificación

Access and refresh tokens are both JWTs carrying a `jti` and a `type` claim (`access`/`refresh`),
so one can't be replayed as the other. Refresh tokens (7-day default) use rotation: each
`/v1/auth/refresh` call deletes the presented token's Redis allowlist entry
(`refresh_session:{jti}`) and issues a new pair — a second use of the same refresh token (replay)
finds no allowlist entry and is rejected. `/v1/auth/logout` writes the access token's `jti` to a
`revoked_access:{jti}` key and deletes the refresh token's allowlist entry. Both key families use
Redis `EX` set to the token's remaining lifetime, so revoked/rotated entries self-expire — no
cleanup job needed. Redis was chosen over a Postgres table for this because the data is
inherently TTL-shaped and read on every authenticated request; a DB table would need its own
expiry sweep and adds a query to the hot path. Per `.claude/rules/security.md`, tokens are
returned in the JSON response body, never a cookie — this API has no cookie-based auth surface,
and CORS runs with `allow_credentials=False`.

### Tradeoffs y Consecuencias

- **Positivas (+):** access-token revocation is immediate (checked on every request via
  `get_current_access_claims`); refresh-token replay after rotation is rejected; no scheduled
  cleanup job, since Redis TTLs expire entries automatically; `TokenService`
  (`app/services/token_service.py`) is framework-agnostic and unit-tested against `fakeredis`.
- **Negativas (-):** adds Redis as a new runtime dependency (`docker-compose.yml`, `REDIS_*` env
  vars) — a Redis outage blocks login/refresh/logout and every authenticated request (the
  revocation check is on the read path). Only one active refresh token per issuance is tracked;
  there's no multi-device session listing or per-device revocation ("log out everywhere" would
  need to revoke by user id, not implemented here) — out of scope for the challenge's time box.

## ADR-007: Task List Aggregate (`TaskListModel`, owner-scoped)

**Status:** Propuesto
**Fecha:** 2026-09-18

### Contexto y Problema

The spec requires list-scoped task management: create/get/update/delete task lists, tasks nested
within a list, and filtered listing with a completion percentage. The schema only had a flat
`tasks` table with no notion of a list, so list CRUD (use case a.i) had nowhere to live.

### Opción Elegida y Justificación

Introduce `TaskListModel` (`app/models/task_list.py`) as its own aggregate — `id`, `name`,
`description`, `owner_id` (FK to `users.id`), timestamps — with a full repository/service/router
stack (`TaskListRepository`, `TaskListService`, `app/api/v1/task_lists.py`) mirroring the existing
`Task` stack 1:1. `owner_id` is set from the authenticated user on create, matching the pattern
where authorization re-reads from the DB rather than trusting a token claim. Task lists own tasks
via a future `list_id` FK on `TaskModel`, deliberately not added in this change to keep the
aggregate introduction isolated and reviewable on its own.

### Tradeoffs y Consecuencias

- **Positivas (+):** list CRUD (create/get/update/delete) is fully implemented and tested,
  independent of the tasks table, so this change doesn't touch `TaskModel`/`TaskRepository`/
  `TaskService`/`tasks.py` at all; the `TaskListNotFoundError` -> 404 handler follows the same
  domain-exception-to-HTTP-status mapping as every other resource.
- **Negativas (-):** `TaskModel` does not yet reference `task_lists` — there is no `list_id` FK, no
  `relationship()`, and no way to nest a task under a list or compute a list's completion
  percentage yet. That linkage, plus filtered/nested listing, is an explicit follow-up; this ADR
  stays `Propuesto` until it lands, since the list↔task relationship the spec actually asks for is
  incomplete without it.
