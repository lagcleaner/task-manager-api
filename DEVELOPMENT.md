# Development setup

Local dev environment from zero, using `uv` (Astral). Target: under 2 minutes.

## 1. Install uv

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
uv --version   # verify
```

`uv` manages the Python interpreter, virtualenv, and dependency resolution — no separate
`pyenv`/`pip`/`virtualenv` needed.

## 2. Clone and install deps

```bash
git clone <repo-url> task-manager-api
cd task-manager-api
make setup     # == uv sync
```

`uv sync`:
- Creates `.venv/` in the project root if missing.
- Installs the exact versions pinned in `uv.lock` (main deps + `dev` group).
- Installs the Python interpreter version pinned by `requires-python` if not already available.

## 3. Environment variables

```bash
cp .env.example .env
openssl rand -base64 24   # -> POSTGRES_SUPERUSER_PASSWORD
openssl rand -base64 24   # -> POSTGRES_MIGRATOR_PASSWORD
openssl rand -base64 24   # -> POSTGRES_PASSWORD
openssl rand -hex 32      # -> JWT_SECRET_KEY
```

Never commit `.env`. `.env.example` only holds non-functional placeholders.

## 4. Run it

```bash
make dev       # uv run fastapi dev app/main.py, http://localhost:8000
```

Or the full stack (API + Postgres) via Docker:

```bash
docker compose up --build
```

## 5. Editor integration

`uv sync` creates a standard `.venv/` at the project root. Both VS Code and PyCharm auto-detect
it:

- **VS Code**: open the project, run `Python: Select Interpreter`, pick
  `.venv/bin/python`. If it isn't offered, add it manually — no extra config file needed since
  `.venv` sits at the workspace root.
- **PyCharm**: `Settings > Project > Python Interpreter > Add Interpreter > Existing`, point at
  `.venv/bin/python`.

## Everyday commands

| Command        | Does |
|----------------|------|
| `make setup`   | `uv sync` — create/refresh `.venv` from `uv.lock` |
| `make dev`     | Run the API with reload |
| `make lint`    | `ruff check` + `ruff format --check` + `mypy` (no fixes) |
| `make format`  | `ruff check --fix` + `ruff format` (auto-fix) |
| `make test`    | `pytest` with coverage report |
| `make migrate` | `alembic upgrade head` |
| `make migrate-new msg="..."` | New autogenerated Alembic revision |

This repo standardizes on `ruff` for both linting and formatting (it replaces
flake8/black/isort — running all four would fight over the same job). Never invoke
`python`/`pytest`/`ruff` directly; always go through `uv run <cmd>` (or `make`) so the
project's `.venv` is used.

## Code quality and git hooks

Quality gate runs via [pre-commit](https://pre-commit.com), config in `.pre-commit-config.yaml`.

```bash
make hooks-install   # one-time, per clone: installs the pre-commit + pre-push hooks
```

On every `git commit`:

| Hook | Does |
|------|------|
| `ruff-check` | `ruff check --fix` — lint + auto-fix, includes import sort (`I` rule) |
| `ruff-format` | `ruff format` — auto-format |
| `mypy` | `mypy app` — strict type check |
| `check-yaml` / `check-json` | Syntax validation |
| `check-added-large-files` | Blocks files over 1000 KB |
| `trailing-whitespace` / `end-of-file-fixer` | Auto-fix whitespace |
| `no-commit-to-branch` | Blocks direct commits to `main` |

On every `git push`: `pytest -m "not slow"` (fast unit tests only, so pushes stay quick).

Run the full suite manually without committing:

```bash
make hooks-run        # uv run pre-commit run --all-files
```

Skip hooks in exceptional cases (e.g. a WIP commit on a feature branch) with:

```bash
git commit --no-verify
git push --no-verify
```

Use sparingly — CI runs the same lint/type/test checks and will fail regardless.

This repo standardizes on `ruff` for lint + format + import sort (it replaces
flake8/black/isort — running all four would fight over the same job); don't add those tools
back via pre-commit or otherwise.

## Adding or updating a dependency

```bash
uv add <package>              # main dependency
uv add --group dev <package>  # dev-only dependency
uv lock                       # regenerate uv.lock after manual pyproject.toml edits
uv sync                       # apply the lock to .venv
```

Commit `uv.lock` alongside the `pyproject.toml` change — it's what makes installs
deterministic across machines and in CI/Docker builds (`uv sync --frozen` refuses to
proceed if the lock is stale).

## Docker build caching

`Dockerfile` is multi-stage:
1. `builder` stage installs the official `uv` binary, syncs deps in a layer separate from the
   app source (so dependency installs are cached across builds unless `pyproject.toml`/`uv.lock`
   change), then copies the source and re-syncs (`uv sync --frozen --no-dev`) to install the
   project itself.
2. `runtime` stage copies only the built `.venv` + app into a clean `python:3.12-slim` image,
   runs as non-root `appuser`, and never contains `uv`, build tools, or source outside `/app`.

Both `uv sync` calls mount a BuildKit cache (`--mount=type=cache,target=/root/.cache/uv`) so
repeated builds reuse uv's package cache instead of re-downloading wheels.
